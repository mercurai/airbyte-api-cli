# Observability Spine — airbyte-api-cli

> Inherits the workspace base: [../../../../docs/standards/_observability.md](../../../../docs/standards/_observability.md)
> (GitHub: https://github.com/mercurai/data-pipeline/blob/main/docs/standards/_observability.md).
> This document records only this repo's layers, observed/standard rows and drift backlog.
>
> A single-layer Python CLI wrapping the Airbyte internal/public API: `airbyte_api_cli/core/` (HTTP
> client, auth, config, output, registry) + `airbyte_api_cli/plugins/` (86 files — per-resource-type
> command handlers, ~67 endpoints across 16 resource types per the README). No frontend, no Tauri-IPC. The
> CLI itself is a "served" surface only in the sense that it's invoked as a subprocess by Dagster and by
> operators — it calls out to Airbyte, it doesn't serve HTTP.

## 1. Correlation / trace ID

**Observed:** no correlation id minted by this CLI itself. Each `HttpClient.request()` call
(`core/client.py:34`) is independent; nothing threads a single CLI invocation's calls together, nor
forwards an inbound trace id from a Dagster caller.

**Standard (target):** the workspace trace-id source for HTTP services is `X-Request-Id`; for a CLI
invoked by Dagster, adopt Dagster's own `run_id` as the correlation id — accept it via an optional
`--trace-id`/env var and echo it in `_USER_AGENT` or a custom header on outbound requests, so an Airbyte
support ticket can be tied back to the triggering Dagster run.

## 2. Canonical structured event

**Observed:** the CLI already emits one structured record on its error path — `output.error()`
(`core/output.py:69-76`) prints `{"error": error_type, "message": message, "status": status}` as JSON to
stderr. This is close to the spine's base field set already (has `error_kind`-equivalent via
`error_type`, has `message`), but lacks `ts`, `trace_id`, `module`, `event`. Success-path output
(`output()`, `:52-67`) is the tool's actual product (JSON/table/compact data to stdout) and correctly
does NOT try to be a log — this is the right split for a CLI (data on stdout, diagnostics on stderr).

## 3. Error ↔ log pairing

**Observed — met.** `AirbyteCliError` is caught exactly once, at the top-level `main()` boundary
(`__main__.py:170-174`), converted to the one `output.error()` call, and mapped to `exc.exit_code`. No
double-logging across layers.

## 4. Redaction policy

**Observed — the best redaction practice in the whole feeders group.** `AirbyteConfig.to_dict()`
(`core/config.py:104-110`) explicitly masks `token`/`client_secret`/`password` as `"***"` before they can
be printed or serialized — a real, working redaction boundary, not just an absence of leaks by omission.

## 5. Severity → action map

**Observed:** no log-level concept exists (there is no logger — see logging.md §1), but the CLI's typed
`exit_code` per exception class (`AuthError`→2, `ConfigError`→3, `NetworkError`→4, generic `ApiError`→1,
`core/exceptions.py:9-39`) is functionally the CLI-appropriate analog of the spine's severity→action map:
a calling script (Dagster shell-out, systemd) can already branch on exit code without parsing text.
